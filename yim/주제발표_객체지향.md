# 객체지향의 중요 3 요소
클래스(Class)  
→ "휴대폰을 만들고 싶어서 제작한 설계도"
→ 즉, 휴대폰이라는 개념을 정의한 설계도

객체(Object)  
→ "엘지 회사와 협업해서 만든 실제 엘지 휴대폰"
→ 설계도를 바탕으로 만들어진 실제 물건(인스턴스)

메서드(Method)  
→ "전화걸기, 사진찍기, 문자하기" 같은 기능
→ 객체가 할 수 있는 행동(동작)

[개념 차이] : 같은 기능을 하는 코드를 여러 번 복사-붙여넣기 했을 때와, 그 코드를 클래스 안 
             메서드로 만들어서 호출할 때의 차이는 무엇인가요? 나중에 그 기능을 수정해야 
             할 때 각각 어떤 일이 벌어지나요?

** 만약 프로그램 전반에 걸쳐 AI가 "안녕하세요! 무엇을 도와드릴까요?"라고 인사하는 코드가 필요해서, 이를 50번 복사해서 붙여넣었다고 가정해 봅시다.

그런데 갑자기 서비스 정책이 바뀌어서 "반갑습니다! 오늘 어떤 코딩을 도와드릴까요?"로 인사말을 수정해야 하는 상황이 벌어졌습니다.

1. 복사-붙여넣기를 했을 때 일어나는 일
수정 과정: 50개의 코드가 위치한 파일들을 일일이 찾아다니며 50번 모두 수동으로 수정해야 합니다.

발생하는 문제점 : 귀찮음과 시간 낭비, 인간의 실수(빼먹는일발생), 오타 위험 등등

한 줄 요약: 수정할 때 고칠 부분이 **N개(복붙한 횟수만큼)**가 되며, 실수할 확률이 극도로 높아집니다.

2. 클래스 안의 메서드(Method)로 만들었을 때 일어나는 일
이 기능을 ChatHelper라는 클래스 내부의 say_hello()라는 메서드로 딱 한 번만 정의해 두고, 필요한 50군데에서는 이 메서드를 호출만 하도록 만들었다고 가정해 봅시다.

Python
# 1. 클래스 내부에 메서드로 딱 한 번만 정의해 둠
class ChatHelper:
    def say_hello(self):
        # 나중에 수정할 때 여기 딱 한 줄만 고치면 끝!
        print("반갑습니다! 오늘 어떤 코딩을 도와드릴까요?") 

# 2. 필요한 50군데에서는 호출만 함
helper = ChatHelper()
helper.say_hello()  # 1번째 곳
helper.say_hello()  # 2번째 곳 ... 50번째 곳까지 똑같이 사용

수정 과정: 클래스 안에 있는 say_hello 메서드의 내용 단 한 줄만 고치면 끝납니다.

발생하는 결과 (매우 안전함):

이 메서드를 호출하던 50군데의 코드가 동시에, 자동으로, 완벽하게 새로운 인사말값으로 바뀝니다.

단 한 곳만 수정했기 때문에 실수로 빼먹을 일도 없고, 오타가 날 확률도 제로에 가깝습니다.

한 줄 요약: 수정할 때 고칠 부분이 언제나 딱 1개로 고정됩니다.






[실수 포인트] : Azure OpenAI 클라이언트를 사용할 때 이런 코드를 봤어요. client = AzureOpenAI() 
              다음 줄에 response = client.chat.completions.create()를 쓰는데, 왜 client.create()가 
              아니라 client.chat.completions.create()처럼 점을 여러 번 찍나요? 이게 메서드랑 무슨 
              관계인가요?

** 이것은 객체 지향 프로그래밍(OOP)에서 계층 구조(Hierarchy)를 나타내기 위한 설계 방식입니다. 이를 메서드 체이닝(Method Chaining) 또는 속성 접근(Property Access)이라고 부릅니다.

 메서드와의 관계
# 메서드는 객체 안에 정의된 함수입니다.
client.create()라고 못 쓰는 이유는, create 메서드가 client 바로 아래에 있는 게 아니라 chat.completions라는 하위 객체 안에 있기 때문이에요.
따라서 client.chat.completions.create()라고 써야 정확히 그 위치에 있는 메서드를 호출할 수 있습니다.

1. 왜 client.create()가 아닐까요?
만약 client.create()라고만 쓰면, 컴퓨터는 이 create가 무엇을 만드는지 알 수 없습니다.
OpenAI 서비스는 단순히 챗봇 대화만 만드는 것이 아니라, 이미지 생성, 음성 파일 변환, 임베딩 벡터 생성 등 아주 다양한 기능을 제공하거든요.

이 수많은 기능을 깔끔하게 정리하기 위해 폴더 트리 구조처럼 계층을 나누어 놓은 것입니다.

client → AzureOpenAI 클래스의 인스턴스(객체)

chat → client 객체의 속성(attribute), 채팅 관련 기능을 담은 객체

completions → chat 속성 안에 있는 또 다른 객체/속성 (채팅 응답 생성 기능을 담당)

create → completions 객체 안에 정의된 메서드(method)

즉, create만이 메서드(함수)이고, 그 앞의 client, chat, completions은 객체 또는 객체의 속성이에요.

# 메서드는 항상 객체에 속한 함수입니다.

 구조 체계 이해하기
client: Azure OpenAI 서비스에 연결된 전체 기지입니다.

client.chat: 그 기지 안에 있는 "채팅(Chat) 담당 부서"입니다.

client.chat.completions: 채팅 부서 안에서도 "채팅 응답 생성 기능, 문장 완성(Completions) 담당 팀"입니다.

client.chat.completions.create(): 그 팀에게 "결과물을 만들어내라(create 메서드 실행)"고 최종 명령을 내리는 것입니다.

2. 코드의 작동 원리 (객체와 메서드의 관계)
파이썬에서 점(.)은 "~의", "~ 내부에 있는"이라는 뜻을 가집니다.

response = client.chat.completions.create( ... )
client 객체는 내부에 chat이라는 하위 객체를 가지고 있습니다.

client.chat 객체는 다시 내부에 completions라는 하위 객체를 가지고 있습니다.

최종적으로 client.chat.completions 객체가 가진 create()라는 메서드(함수)를 호출하는 것입니다.

# 그럼 객체(Object)란? 뭐지~????
클래스(class)라는 설계도를 바탕으로 만들어진 실제 인스턴스(instance)가 객체입니다.
# 객체는 변수에 담겨서 사용되고, 그 안에는 속성(데이터)과 메서드(동작)가 들어 있습니다.

3. 만약 다른 기능을 쓰고 싶다면?
이 계층 구조 덕분에 코드가 아주 직관적이고 깔끔해집니다. 만약 채팅이 아니라 이미지를 만들고 싶다면 어떻게 쓸 수 있을까요?
# 이미지를 생성할 때는 하위 부서를 'images'로 바꿉니다.
response = client.images.generate( ... )
이처럼 client.create() 하나에 모든 기능을 때려 박는 것보다, client.chat..., client.images... 처럼 역할을 분담해 놓으면 개발자가 코드를 읽고 관리하기가 훨씬 쉬워집니다.




[응용] : Azure ML 파이프라인에서 데이터 전처리, 모델 학습, 배포 기능을 각각 별도 클래스로
 나눈다면 어떤 기준으로 나눠야 할까요? 모든 기능을 하나의 클래스에 메서드로 넣는 
것과 비교했을 때 어떤 장단점이 있을까요?

** 1. 클래스를 나누는 디자인 기준 (Separation of Concerns)
Azure ML 파이프라인에서 기능을 분리할 때는 "단일 책임 원칙(Single Responsibility Principle)"과 "컴퓨팅 자원의 독립성"을 기준으로 삼아야 합니다.


기능 (컴포넌트)	분리 기준 및 역할	Azure ML 관점에서의 자원 최적화


데이터 전처리(Data Preparation)

* 데이터를 로드, 정제, 정규화, 분할(Train/Test)하는 역할

* 데이터 스키마 검증 및 피처 엔지니어링 수행

* CPU와 메모리가 많이 필요한 작업입니다.

* **메모리 최적화 인스턴스(High-Memory CPU)**를 할당하는 것이 효율적입니다.


모델 학습(Model Training)

* 전처리된 데이터를 받아 모델을 학습하고 평가하는 역할


* 하이퍼파라미터 튜닝 및 학습된 모델 파일(지정된 포맷) 저장

* 연산량이 극도로 많은 작업입니다.

* **GPU 인스턴스(Compute Cluster)**를 할당하여 비용과 시간을 아껴야 합니다.


모델 배포(Model Deployment)

* 평가를 통과한 모델을 Azure Container Registry(ACR)에 등록


* 온라인 엔드포인트(Managed Endpoint) 또는 배치 엔드포인트로 배포

* 연산보다는 클라우드 인프라 조작이 주를 이룹니다.

* 가벼운 기본 CPU 인스턴스나 로컬 환경에서도 실행 가능합니다.


2. 구조 비교: 하나의 대형 클래스 vs 독립된 컴포넌트 클래스

 모든 기능을 하나의 클래스에 넣는 경우 (Monolithic)
하나의 거대한 PipelineManager 클래스를 만들고, 그 안에 preprocess(), train(), deploy() 메서드를 모두 집어넣는 방식입니다.

장점: 

소규모 토이 프로젝트나 로컬 실험 단계에서는 파일 하나만 관리하면 되므로 직관적이고 빠르게 작성할 수 있습니다.

클래스 내부 변수(self.data, self.model)를 통해 데이터를 쉽게 주고받을 수 있습니다.

단점 (Azure ML 파이프라인 구축 시 치명적):

자원 낭비 (비용 폭탄): 학습을 위해 GPU 장비를 띄웠는데, 데이터 전처리와 배포 단계에서도 그 비싼 GPU 장비가 계속 켜져 있어야 합니다.

재사용 불가: 데이터 전처리 로직만 가져와서 다른 실험에 쓰고 싶어도, 학습과 배포 코드가 얽혀 있어 분리하기 어렵습니다.

캐싱 효율 저하: Azure ML은 변경되지 않은 단계의 결과를 캐싱(Reuse)하는 기능이 있습니다. 하나의 클래스에 묶여 있으면 전처리 코드만 살짝 고쳐도 모델 학습까지 처음부터 다시 실행됩니다.

 각 기능을 별도 클래스로 나누는 경우 (Component-driven)
DataPreprocessor, ModelTrainer, ModelDeployer 세 개의 독립된 클래스(또는 별도의 파이썬 파일)로 나누는 방식입니다.

장점:

컴퓨팅 인프라 최적화: 전처리는 CPU 클러스터에서, 학습은 GPU 클러스터에서 독립적으로 실행시켜 클라우드 비용을 극적으로 절감할 수 있습니다.

강력한 캐싱(Caching): 데이터 전처리 로직이 바뀌지 않았다면, Azure ML은 전처리 단계를 건너뛰고 기존 저장된 데이터를 로드해 곧바로 학습 단계(GPU)로 넘어갑니다. 시간과 자원이 엄청나게 절약됩니다.

유지보수 용이성: 학습 알고리즘(예: LightGBM에서 PyTorch로 변경)을 바꿀 때, 전처리나 배포 코드는 손댈 필요 없이 ModelTrainer 클래스만 수정하면 됩니다.

단점:

전처리 단계의 출력물(데이터)을 임시 스토리지(Azure Blob Storage 등)에 저장하고, 학습 단계에서 이를 다시 불러오는 파일 입출력(I/O) 코드가 추가로 필요합니다.

파일이 여러 개로 쪼개지므로 초기 구조 설계에 공수가 조금 더 들어갑니다.


 Azure ML 파이프라인 표준 구조 예시

실제 Azure ML SDK v2를 사용할 때는 아래와 같이 각 클래스를 독립된 컴포넌트로 정의하고, 이를 파이썬 스크립트 형태로 엮어 관리합니다.

my_aml_project/
│
├── components/
│   ├── preprocessing.py  # DataPreprocessor 클래스 포함
│   ├── training.py       # ModelTrainer 클래스 포함
│   └── deployment.py     # ModelDeployer 클래스 포함
│
└── pipeline_job.py       # 세 컴포넌트를 Azure ML 파이프라인으로 연결하는 메인 스크립트
메인 파이프라인 연결 스크립트 (pipeline_job.py 개념)
Python
from azure.ai.ml import dsl, Input, Output

# 별도로 분리된 컴포넌트들을 불러왔다고 가정
from components.preprocessing import azureml_prep_component
from components.training import azureml_train_component
from components.deployment import azureml_deploy_component

@dsl.pipeline(description="Azure ML MLOps 파이프라인")
def machine_learning_pipeline(raw_data):
    # 1. 전처리 단계 (CPU 환경에서 실행)
    prep_job = azureml_prep_component(input_data=raw_data)
    
    # 2. 학습 단계 (GPU 환경에서 실행 - 전처리 결과를 입력으로 받음)
    train_job = azureml_train_component(training_data=prep_job.outputs.clean_data)
    
    # 3. 배포 단계 (기본 환경에서 실행 - 학습된 모델을 입력으로 받음)
    deploy_job = azureml_deploy_component(model_folder=train_job.outputs.model_output)
    
    return {"pipeline_output": deploy_job.outputs.endpoint_uri}
결론적으로, 단순 로컬 테스트가 아니라 Azure ML이라는 클라우드 오케스트레이터의 장점(비용 절감, 캐싱, 자원 분배)을 100% 활용하기 위해서는 반드시 기능을 별도의 클래스와 컴포넌트로 분리하는 것이 좋습니다.
